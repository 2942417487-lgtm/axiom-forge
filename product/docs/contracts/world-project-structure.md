# 标准世界项目目录规范

本文件维护行为与数据约束；实现范围、合入状态和工程验收统一见 开发当前状态（开发记录随源码仓库提供）。规范、合成示例及未来验收条件不授予执行权限。

用户确定：一项目一世界观、多对话，采用本文目录职责、元数据含义、四领域用途和关联边界。新电脑 A 直接 clone 同一 GitHub 仓库，在系统中打开／登记／校验后接续修改，经工作分支、PR、自检、用户复查及明确通过后合并；B 请求同仓库合并版本更新。完整包不是这些操作的前置条件，离线封装参考留待未来。本文沿用已有核心目录，不授权实现或发布；资料解析、隐私、审批要求见 [主契约](world-portability-contract.md)，接续流程见 [仓库协作规范](world-git-sync.md)。

## 2. 项目逻辑布局

以下是一份外部世界项目的逻辑布局。注释标明既有部分和规范已定义但未实现的扩展；本系统开发仓库不存放正式世界内容。

```text
<世界项目>/
  project.json                 已有字段 Schema／只读检查；创建、登记与迁移未实现
  README.md                    扩展：项目说明与阅读入口
  world/                       既有：正式结构化世界知识
    world.json                 世界身份与基本描述
    canon/
      physics/
      astronomy/
      technology/
      engineering/
      economy/
      society/
      politics/
      history/
    timeline/
    actors/
    assumptions/
    evidence/
    audits/
    decisions/
    snapshots/                 既有：知识快照；不提供执行恢复权限
  documents/                   未实现：作者文稿与说明
    overview/                  简介、故事梗概等
    setting-notes/             设定说明、世界历史与角色文稿
    reasoning/                 逻辑链、论证说明
    drafts/                    未定稿内容；不自动成为 Canon
  calculations/                未实现：问题、模型、输入、结果与程序文本
    <计算记录标识>/
  research/                    未实现：可共享、不可执行的历史研究档案
    conversations/<对话标识>/  历史对话文本与资料关联
    tasks/<来源任务标识>/      分析、审查、工具回执、提案等安全副本
  assets/                      未实现：项目拥有的附件、媒体与数据
  indexes/                     未实现：跨文件关系及附件／外部引用登记
    relations.json
    attachments.json
    external-resources.json
  exports/                     未实现：已生成的介绍文件及配套媒体
    introductions/
  .gitignore                   既有：共享边界的忽略规则
  .git/                        既有：原生 Git 版本管理；各机由 clone 建立，不复制源配置
  .axiom/local/                既有：私人执行状态；保留本机，不共享
```

目录职责及用途依本规范执行；JSON 字段、计算记录标识与机器格式仍待细化。不存在的模块不要求现在创建空目录。用户自建的安全文件及目录也属于项目内容，不能因为不在示例树中就被丢弃。

### 2.1 各层的权威性

- world/world.json 是现行世界身份的权威来源。project.json 的职责是描述产品项目，不另建一份可以独立改写 world_id 的真值；若登记关联 world_id，必须与前者一致。导入仍由宿主绑定目标项目／世界，源项目标识不授予目标权限。
- world 是已经接受的结构化知识；documents 可以解释它，也可以包含待定设定。两者冲突时展示差异，不能用文稿静默覆盖 Canon。历史快照和未提交编辑须分别标明基线与候选。
- research 保存边界内的历史内容与关联，不能直接复制 .axiom/local。可共享历史内容须先按安全字段整理成独立只读档案、说明排除项并经审查纳入 Git；整理／持久化入口尚未实现。clone 只取得已上传档案，不自动迁移本机活动记录。敏感字段与安全副本逐项登记，不能任意删减研究内容。
- calculations 的脚本是数据，不成为宿主已审核程序登记；历史计算结果不冒充本次实算。
- indexes 负责定位、关系和覆盖。已有对象内的正式引用仍以原记录为准；可重建索引需要记录输入版本和生成规则，失配时报告或交付重建候选，不能反向自动改写知识。外部资源登记不表示已下载、提交或随 clone 取得。
- assets 保存项目实际拥有的内容；大型论文仍可置于外部资料库并登记引用。明确实际提交／取得的附件、LFS 内容和仅外部引用项，不能以提交已同步声称所有媒体都已取得。
- exports/introductions 保存将来生成的作品，不是本轮 0 字节规范占位文件。项目介绍文件保留其自身版本／日期及内容关联；不能用它替代 world 和原始档案。

### 2.2 项目元数据的含义

project.json 的元数据用途已确认。2026-10-09 的 [字段级契约](project-metadata-contract.md) 定义 project_format_version、project_id、world_id 关联与 display_version 四字段，2026-10-10 已获准最小实现 Schema／PRJ／[只读检查](../guides/project-metadata-check.md)；完整产品登记、创建和多个对话仍未实现。这里的“项目”是产品中新建／打开的世界项目，其元数据承担以下职责：

| 概念 | 含义 | 与现行数据的关系 |
| --- | --- | --- |
| 业务项目身份 | 系统用于识别某个项目容器的稳定标识，关联该项目的对话、附件和档案 | 一项目绑定一世界；world_id 识别世界，workspace_id 识别本机工作区绑定；用户已确认同一仓库跨机保留 project_id，各机新建 workspace_id。源标识不替代宿主选择的目标身份 |
| 展示版本 | 用户给世界作品标注的可读版本，例如“第二版”或“v1.2”；供介绍文件、审阅与发布说明使用 | 草案以 project.json 的 display_version 作为唯一当前标签，未设置时为 null；不另维护漂移副本，不是 Canon 哈希、Git 提交或系统软件版本 |
| 结构格式版本 | 表明项目采用哪版目录／字段组织规范，帮助解析者判断兼容性 | 世界故事或设定改动不必改变此版本；未来组织方式或字段契约发生不兼容变化时才依迁移规则处理，不凭版本号自动重排文件 |

project.json 不复制已有 world/world.json 的世界名称／描述真值，也不保存 API 凭据、厂商会话或本机恢复绑定。world_id 仅作与世界权威文件一致的关联，不能独立重定世界。本步新增元数据 Schema 和合成示例，不生成正式项目文件；完整仓库回执／资料映射继续另定。

### 2.3 四个 Canon 领域（用户已指定用途）

| 目录 | 归档用途 |
| --- | --- |
| canon/physics | 偏理论设定，描述世界采用的物理规律、理论模型与基础原理 |
| canon/astronomy | 天文学设定，如恒星、行星、轨道与天体环境 |
| canon/technology | 应用技术设定，包括材料学、材料性能／制备及可用技术能力 |
| canon/engineering | 具体工程设定描述，包括系统构成、尺寸／资源／制造等约束、工程可实现性与项目经济性说明 |

目录枚举本身不变。跨领域内容通过实体依赖和引用关联，不为归档在多个目录复制可以独立修改的同一条设定。工程项目的成本／收益／可维护性说明可保留在 engineering，并引用 economy 的资源、价格、产业与经济环境前提；不因涉及经济性而强制搬出工程条目。工程／经济研究岗位仍按各自职责分析，内容目录不等于岗位权限或派发规则。

领域表达“讨论哪类内容”，知识状态表达“内容被接受或确认到什么程度”。physics 或 technology 中也可以有假设状态，文件进入 canon 目录不会自动成为 Hard Canon 或经验证的现实事实。本文例子仅用于解释用途，不代表任何真实世界研究结论。

### 2.4 假设、审计、决策与知识快照

已核对现行 [假设格式](../../resources/schemas/assumption.schema.json)、[审计格式](../../resources/schemas/audit.schema.json) 与 [决策格式](../../resources/schemas/decision.schema.json)：三者继承 CanonEntry，只固定各自 domain。当前具有标题、陈述、状态、来源、依赖、影响、冲突、Evidence／Claim 关联与更新时间等通用字段，没有完整专用假设参数表、审计过程或决策审批日志 Schema。下面是用户已确认的内容用途规范，不声明新增字段或自动操作已实现。

| 目录 | 适合保存的内容 | 与其他设定的关系 |
| --- | --- | --- |
| assumptions | 明确但仍有条件／不确定性的研究前提；建议集中登记会被多个条目复用的前提，例如假定某种材料已能稳定批量制造 | Canon 条目可用 dependencies 引用 ASM 身份；变化时检查依赖结论，不自动修改下游。仅某次计算临时采用的前提先保存在对应计算／任务记录，不把所有临时参数都提升成全世界共享假设 |
| audits | 经选择保存的世界设定审查结论，例如某工程方案的热控制、制造或经济性问题、适用条件与未解决项 | 引用被审条目、假设与 Evidence，完整研究过程见对应 tasks 档案。这里审的是世界设定；系统软件代码审查仍属于系统开发记录 |
| decisions | 设定取舍与理由，例如为什么选某工程方案、放弃替代方案，参考哪些审查与证据 | 关联涉及的设定及审查；历史批准可写成无执行权限的叙述。决策条目本身不是签名批准或 Apply 回执，不授予 Canon 写入／恢复权限 |
| snapshots | 已实现：某时点结构化知识文件的固定内容、路径、内容校验及世界／Canon 版本 | 当前覆盖 world.json、八个 Canon 领域及 timeline／actors／assumptions／evidence／audits／decisions；供任务固定基线、追溯和比较。不包含文稿、媒体、全部项目档案、Git 提交图或运行恢复状态 |

假设的领域与其状态不能混为一项：现行格式没有要求 assumptions 中所有条目必须为 Assumption 状态，也没有自动将已接受前提迁移到其他领域。假设证据或状态改变时需形成可审查变更，具体跨类型迁移另行设计，不由导入器自行搬动记录或改 ID。

### 2.5 对话档案与任务档案

conversations 保存用户与系统交流的历史内容、所关联资料、提出的问题和取舍；便于以后浏览、检索、引用原文，或把所选材料交给新任务。它记录“聊过什么”。导入后的档案是可读内容，不恢复厂商 Session，也不自动拼入每个新对话的模型上下文；实际浏览／检索／引用入口尚未实现。

tasks 以具体研究问题组织历史材料：问题、当时知识快照、各岗位分析、交叉审查、工具读取／计算回执、综合结果、待审提案及最终处理的历史说明。它记录“这个问题怎样研究、检查并得出结果”。一次对话可提出多个任务，任务也可关联多个对话；二者用业务身份／引用连接，不强制一对一，不另生成可独立漂移的重复内容。

原始材料和工具结果需保留原状态与出处；摘要仅作阅读辅助，不能代替完整记录。档案整理保留可共享业务内容并给出只读映射，不将原活动 TaskState 直接搬运为可执行对象；MAC、continuation、费用预留或执行恢复权限仍排除。未完成问题若要继续，从历史档案选择问题／资料并启动新任务，绑定当前世界与固定快照；不能将旧档案直接注册为待恢复执行状态。

引用历史对话和任务仍受同世界／目标绑定、用户选择、未审内容隔离与研究首轮独立约束。不能把本任务其他岗位的首轮结果包装成“历史聊天”绕过隔离。已归档并提交的安全研究内容可以随仓库共享；未归档本机记录另列覆盖缺口。提示词规范不代表上述持久化／解析功能已实现。

## 3. 未来可选离线包的结构参考

首版契约采用第 2 节原生项目路径，不增加 project/ 前缀、包 manifest 或历史封装。以下保留此前包设计供未来参考，移出首版验收与工程依赖；不表示现在需要建立或导出包。

未来若启用完整包，仍沿用项目目录职责与原相对路径，不重排成另一套 knowledge／archive 目录；候选外层封装如下，具体容器格式推迟：

```text
<完整数据包>/
  manifest.json                导出清单、边界处置、版本与内容校验
  history/
    repository.bundle          候选：自包含 Git 历史载体
  project/                     项目文件的边界过滤副本
    project.json
    README.md
    world/
    documents/
    calculations/
    research/
    assets/
    indexes/
    exports/
    .gitignore
    <其他边界内项目文件>
```

project 下的相对路径与原项目一致，例如原 world/evidence/EVD-xxx.json 仍在 project/world/evidence/EVD-xxx.json。manifest 与 history 是封装层信息／历史载体，不重排业务目录；历史保留必备，具体压缩形式、扩展名和 bundle 版本继续细化。Git 来源提交与项目文件／草稿差异分别核对，不将未提交内容说成已经合并。

打包以整个项目文件清单为输入，再按已确认边界排除或生成脱敏副本，不采用只收几个已知目录的隐含白名单。原件和本机 .axiom/local 必须保留；最终包及清单不能携带真实秘密、可信执行配置或可激活的私人状态。历史安全视图的生成及映射规则尚需正式定义。

未来生成的完整包建议输出到项目之外，避免把正在生成的包再次纳入自己。项目内已存在的旧包或其他安全文件仍应登记；它们的重复内容／敏感问题需审查，不能暗中省略。脱敏导致的路径、关系或知识版本变化按主契约处理。

若未来采用完整包，保留原 Git 历史的原则继续有效；文件树、研究档案、知识快照与 Git 历史分别登记。历史载体须自包含并保留声明的提交／分支／合并关系，排除本机配置和执行状态；来源含秘密时停止外发，不自行省略或重写。此项不是首版打包要求，见 [后续离线参考](world-git-sync.md)。

## 4. 仓库接续、协作与介绍文件

GitHub 世界仓库是换机和多人协作的主路径。A 直接 clone 并打开／登记／校验，B 取回明确提交、比较后人工接受更新；保留原生历史及本机状态隔离。仓库访问机制提供协作权限，工作分支／PR、自检、用户复查和明确合并批准仍需遵守。

介绍文件用于让他人理解世界，保留 .md／.pdf／.html 导出方向；详细规范仍只留 [空占位文件](world-introduction-export.md)。介绍不能恢复完整世界数据。未来离线包与原生仓库共用内容边界，但不替代正常 clone 或提供执行／上传权限。

未来 GitHub 流程：明确选择世界与仓库 → 本地工作分支及必要 Canon 审批 → 上传前敏感内容、待上传历史及自动执行入口检查 → 推送工作分支并提交 PR → 自检并报告结果 → 用户复查本次内容 → 用户明确批准后才合并。认证只由外部宿主管理；批准绑定源提交、目标基线和预计合并内容，变化后须重新检查与用户复查。自动执行状态未知时停止上传，分享文件不授予程序执行权限。具体要求见主契约第 4.3 节。

本轮只确认并修改规范。本文未生成任何正式世界文件，没有配置 remote、提交 PR、上传文件或合并。
