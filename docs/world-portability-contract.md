## 3. 项目、世界观与对话身份

用户已确认：一个项目对应一个世界观，一个项目可有多个对话。当前仓库有 WorldWorkspace／world_id／Task／Run 等基础，没有完整产品 Project／Conversation UI 或它们的正式 Schema，以下是未来交互规范。

目标身份由可信宿主选择，不能由文件中的名称、提示词、manifest 或模型自己改变。仓库打开／登记至少绑定目标项目、世界、工作区、精确提交及知识基线；对话资料导入另绑定 project_id、world_id（未绑定新项目可为空）、conversation_id、import_id 和输入身份。文件内的 source_world_id 是来源声明，不能替代目标身份。

项目的“打开”只选择现有项目，不意味着导入内容可以覆盖它。新项目可先处于未绑定世界身份的准备状态；已 clone 的原生仓库经宿主校验与用户接受后，才关联来源 world_id 并建立新工作区绑定；不会要求先打包或让模型重建知识。此准备状态尚未实现，不等于现有 CLI world create 已支持延后身份初始化。

隔离规则：

1. 新机器接续同一世界仓库：保留经校验的 source world_id 与提交历史；新建随机 workspace_id、路径绑定和外部宿主配置，不复用原私人执行状态。project_id 的跨机映射待机器契约细化。
2. 现有项目接收同世界版本或资料：绑定当前基线，比较精确提交、对象 ID、内容与关联；不能仅因 ID 一样就覆盖。仓库更新与对话资料接受分别处理。
3. 原文件无 world_id：使用当前目标项目作为待审归属，显示来源身份未知，不能按标题相似自动认定同一世界。
4. 来源 world_id 与目标不同：停止常规应用，明确展示两个身份；可在当前对话只读审阅外部世界，但不能自动混入目标 Canon。用户若要跨世界参考／改编，需独立、可审查的 ID／关系映射方案。
5. 多个项目中名称或局部实体 ID 相同：以世界／项目身份和对象类型区分；禁止全局以 TECH-001、名称或对话标题串用对象。
6. 同项目多对话可共享已经接受的世界知识，但导入暂存与未审结果绑定各自 import_id；不能默认读取其他对话的未审私有内容。
7. 同一研究任务启动后仍固定 Canon Snapshot；其他对话接受新内容不能改变运行中任务的快照。

项目选择错误、并发更新、基线变化或输出身份不匹配时停止应用，重新交付比较结果。不能把“打开已有项目”理解为“恢复另一个机器的旧 Task／Session”。

## 4. 世界项目的共享数据边界

用户已确认：纳入可审阅历史对话、研究过程、工具回执与待审提案，排除密钥、厂商会话凭据及可执行审批／恢复状态。这一边界适用于项目归档、GitHub 共享和未来离线包，不是任意宿主目录复制。

共享历史须先整理成独立安全档案，保留业务内容及关联、说明排除项，再经审查纳入 Git；此整理接口尚未实现。clone 不自动取得未提交文稿、未归档本机研究记录或未下载的附件。实际共享／获取覆盖必须列明。

以下五类说明内容边界，不要求重排目录，也不是新增现行 Schema；原生项目路径见 [目录规范](world-project-structure.md)，第 5 节仅为未来离线包参考：

| 类别 | 应保留的内容 |
| --- | --- |
| 正式世界知识 | 世界描述、设定、Actors、历史／时间线、假设、审计、决策、Claims、Evidence 及它们的索引／关系 |
| 作者项目内容 | 简介、故事梗概、介绍正文、草稿、图表、逻辑链和用户加入的说明文件；不强塞进现有 CanonEntry |
| 计算与技术档案 | 问题、模型／公式、单位、输入、假设、程序文本、原始结果、数据、计算记录及引用 |
| 历史研究档案 | 可分享的对话、分析、审查、Red Team、综合、工具回执、待审提案、历史快照／版本和溯源记录 |
| 项目附件 | 用户加入项目的图片、音频、视频、文档、论文及其他资料，或明确登记的外部资源引用 |

原始大型论文继续默认放外部资料库，不因本规范加入系统 Git。分享资料与跟踪进系统／世界 Git 是不同决策。仅链接而没有实际内容的资源标为 external_reference／unavailable；LFS 指针与实际媒体分别检查，不能宣称已随 clone 取得或可离线使用。

### 4.1 禁止直接搬运的状态

- API Key、Token、密码、cookies、带认证参数的 URL、审批 Key、Secret Store 内容和其他认证秘密。
- 厂商可复用的 Session／Thread／continuation／登录身份与凭据。
- 原工作区绑定、锁、调用游标、checkpoint、费用预留和自动续跑所需执行状态。
- 可被宿主执行的批准／拒绝／Apply／恢复回执，包括签名／MAC 与可恢复的提交准备记录。
- 宿主配置、个人绝对路径、代理认证、Git credential、hooks、filters、外部驱动配置和安装环境。
- 任何会被作为可信执行规则加载的岗位／Schema／路由／程序登记。用户文件中的规则或程序可作为不可信文本材料保留，不能自动加载或执行。

不得整目录复制源电脑的 .axiom/local 或 .git。原生 Git 通过标准 clone／fetch 接续；宿主提供研究材料的独立只读安全视图，不搬运整个活动状态。源目录及原始模型输出不为共享而覆盖，Git 不自动完成档案转换。

历史记录可以保留业务 TSK／RUN／ARN／ART／CHG 标识作为来源标签，文件与关系引用也要保留；导入后不注册为当前执行中的 ID，不据此恢复调用或批准 Canon。批准曾发生的事实可保存为不含签名权限的历史叙述，并明确“不可执行”。原始工具回执可能含路径／headers／秘密，不能因为是历史档案就跳过敏感检查。

可分享配置与用户定义的世界设定参数属于内容；认证 endpoint／Key／操作权限属于宿主。混合文件必须交付脱敏副本和排除清单，不能将整份文件一概保留或偷偷删除安全字段后称原样无损。

### 4.2 原生 Git 历史与版本

世界仓库接续保留实际取得的原生提交标识、父关系及所选远端分支／标签，不为打开项目重建空 Git 或用模型摘要替代。固定源提交、world_id、知识基线和历史／资料覆盖；浅历史、过滤对象、未取得的 refs 和不在远端的本地提交不能声称完整接续或完整备份。

“原 Git 提交图”是历史提交及其父子关系，包括分支发展与合并。提交含对应文件树、父提交、作者／时间及说明，依据 [Git 官方对象说明](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)。世界展示版本、知识快照与 Git 精确提交各自记录，不能因文件树相同就声称是同一提交。

可信宿主负责受限取得、实际接收对象／metadata／文件的安全检查、身份与基线校验；不复制旧仓库配置、hooks、credential 或本机执行状态，不从来源 remote 声明取得连接权限。秘密检查覆盖历史而不只检查最新树；发现问题停止外发及接受，交用户处理，不自动重写历史或 force push。具体流程见 [仓库接续规范](world-git-sync.md)。

完整包的历史保留原则仍作为未来参考；自包含 Git bundle 等载体封装已推迟。首版接续不要求 manifest、bundle 或包导入器。

### 4.3 世界项目的 GitHub 规范

用户已明确世界项目支持 GitHub：工作分支 → PR → 自检 → 用户复查 → 明确通过后合并。本节确定未来操作规范，当前尚未实现世界 GitHub 接入，也不是本轮配置 remote、上传当前文档或合并 PR 的授权。

- 显式绑定当前世界、独立世界仓库和目标 remote；不得按世界名称猜测仓库，不复用系统仓库 origin 或其他世界的连接。认证 Key、Token 与 credential 配置只由外部宿主管理，不写入项目内容或日志。
- 上传前先检查明确文件清单、实际待上传内容和会随 push 发送的提交历史；发现疑似秘密或禁止共享的状态时停止上传并安全定位。PR 自检继续检查内容与关系、适当的数据校验和差异，记录真实结果及覆盖限制；不能等 PR 已上传后才首次检查秘密。
- 上传前也核对项目及目标 remote 的自动执行／发布入口，包括 .github/workflows、既有 CI／App 和可能执行项目内容的配置。push／PR 可以触发工作流，工作流可能访问仓库 secrets，不能把用户的文件分享请求等同于程序执行授权。相关入口及权限未知时停止上传，交付待确认事项；只复用已经审查、在授权范围内的执行，或确认相关自动执行已经禁用。新增／改变执行能力须单独审查并获授权；可共享项目仍将此类安全文本作为不可信数据保留，不能偷偷遗漏。依据 [GitHub 工作流触发说明](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow) 与 [工作流秘密访问说明](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets)。
- 私密文件、.axiom/local、审批 Key、可执行批准／恢复状态和厂商可复用会话不得上传。历史研究只上传边界内安全档案；大型资料继续按外部资料库策略处理，不因启用 GitHub 自动追踪。
- .gitignore 是辅助规则，不能排除已经被跟踪的文件或旧提交里的秘密。当前版本删除 Key 不代表旧历史已安全；秘密不得因仓库为 private 而获准上传。发现历史问题时停止，交付处理建议，不擅自重写历史、强制推送或删除分支。
- PR 自检完成后，用户复查源提交 SHA、目标仓库／分支及其基线 SHA、预计合并后的内容与关系、对应差异和检查结果。明确批准绑定这一份合并投影；源提交或目标基线变化、合并策略变化而影响投影时，都需要重新检查并交用户复查，不沿用旧批准。执行合并前再次核对该绑定，不能仅比较源 SHA 或目标分支名。未通过、身份不匹配或检查未解决时不合并。
- 现有 Canon 的内容批准与 GitHub PR 的合并批准分别有效。前者仍走 ProposedCanonChange／独立宿主批准／Apply；后者不能让研究岗位获得 Canon 写入权，也不能把一次发布批准解释为之后自动合并权限。

首次发布也先上传工作分支并提交 PR，不将已含正式世界内容的 main 直接作为绕过用户复查的上传路径。目标远端基线的建立方式待 GitHub 接入设计；不把初始空提交许可扩展为无审查的内容发布。

### 4.4 同一世界的多电脑与多人协作

A 直接 clone 同一 GitHub 仓库，宿主校验并经用户接受后打开／登记，建立新本机绑定；在工作分支修改，经 PR、自检、用户复查与明确通过后合并。B 请求同仓库已合并的明确版本，先取回、比较、人工接受，再更新本地。全过程不依赖完整包。

多人通过 GitHub 的仓库访问机制协作，仍按各自工作区、工作分支和 PR 审查；访问权限不替代 Canon 批准或本次合并批准。world_id 保持一致，本机 workspace／凭据／批准／恢复状态独立。并行修改、未提交内容、路径冲突和分叉历史须保留原内容并交付处理方案，不能自动 reset／clean 或重写历史。

共享研究档案不启用旧任务，也不绕过首轮独立和固定快照。仓库获取不会自动取得全部本机记录／外部媒体，更新接受不能成为 Hard Canon 免审通道。具体覆盖、打开／登记、A／B 与多人流程见 [仓库协作规范](world-git-sync.md)。

本节保留此前完整包设计供后续参考，整体移出首版契约依赖和验收。原生仓库直接使用既有项目路径，不增加 project/ 前缀或 manifest；本节的打包、历史封装、离线导入和发布均需以后另行确定范围。

未来完整包的最终封装、扩展名及机器 Schema 尚待审查；.afworld.zip 可作为候选容器，不继续把旧 knowledge-v1 固定容器限制当作用户已确认需求。本轮不注册格式、实现压缩器或要求用户使用新 CLI。

按用户定义，完整包是剔除数据边界之外内容后的完整项目文件。包与项目采用同一目录规范，不再另建 knowledge／archive／references 等重排结构。建议封装如下：

```text
<完整数据包>/
  manifest.json     导出清单、版本、边界处置与文件校验
  history/
    repository.bundle  候选：自包含 Git 历史载体
  project/          原项目文件树的边界过滤副本
    world/          既有核心知识目录，保留原相对路径
    documents/      未实现：作者文稿
    calculations/   未实现：计算档案
    research/       未实现：可共享历史对话与研究档案
    assets/         未实现：附件与媒体
    indexes/        未实现：关系、附件与外部资源登记
    exports/        未实现：已生成的介绍作品
    ...             项目说明、元数据及其他边界内文件
```

完整项目目录及既有／未实现部分见 [项目结构规范](world-project-structure.md)。用户已确认目录职责、元数据用途、假设／审计／决策／快照与历史档案的关联规则，以及 physics／astronomy／technology／engineering 的用途；具体字段和机器契约尚待细化，不创建实际项目目录。world/evidence 等原路径只加 project/ 封装前缀，业务 ID 和字段保留；清单不得替代业务记录，不让导入器靠正文猜目录。

打包枚举整个项目，再按已确认边界处置，不能只收示例目录而漏掉用户自建的安全文件。默认完整范围是全部边界内项目内容；用户主动选择省略非私人内容时应明确列为部分包，不能自报完整。实际包输出建议位于项目外，避免递归包含本次生成的包；已有旧包等文件仍登记并审查。

manifest 至少描述：

- 格式标识、包版本、各类数据契约／映射版本、导出时间、用户世界版本和生成器声明。
- 来源 world_id、源知识版本、Git 基线声明及未提交材料的分类；不强制所有导出内容都已提交。
- Git 历史载体路径／字节校验、对象格式、源提交、HEAD／业务 refs、实际历史覆盖及其与 project 文件／草稿差异的对应；自包含与完整性由可信宿主验证，不由模型自行声明。
- 每项的唯一包内相对路径、类型、原始字节大小／SHA-256、原始业务身份（若有）、来源定位及内容状态。
- 每项的目标模块／建议映射、对象关系、附件依赖、计算与来源关联；未知或没有现行 Schema 的内容进入可审查档案，不能伪造 Schema 已支持。
- 全部 included／excluded／redacted／external／unavailable 项目，排除原因和原引用的替代映射。敏感项只用安全定位，不保存秘密本身。
- 原生知识的 canon_version／哈希 profile；归档、正文与附件有各自哈希，不混入现有 Canon 哈希定义。
- 是否完成此次声明范围的覆盖，以及任何非秘密缺失。该范围由用户确认，不能由模型擅自缩小后自报 complete。

“完整”可保证的是：经确认的可分享内容被枚举、关联、实际保存或明确按所选外部引用策略处理；被排除的秘密与私人执行状态有安全的分类记录。正文中未被识别的秘密、未获取的附件或未枚举材料不能被承诺不存在。

导出涉及脱敏时：仅保存脱敏副本，不改变源文件；标注 redacted、安全位置和影响到的关系。不得把秘密原文、Key 摘录或可还原它的补丁放进包。私人项目原始哈希是否暴露也需考虑，不为了审计默认发布敏感文件的原始哈希。

原生知识 JSON 的正文、metadata、Evidence URL／locator 等被脱敏时，语义哈希和 Canon 版本也可能变化。必须区分 source_canon_version（来源版本声明）与 payload_canon_version（实际包内有效知识内容重算所得版本）；不能继续用来源版本代表脱敏 payload 或称其原样无损。脱敏后的知识与关系差异是候选，向用户展示安全的变更位置／影响及 ID 映射，不展示可恢复秘密的 before 值。已有世界的正式修改仍走 Canon 审批，新项目接受基线也须明确接受脱敏内容而非原版本。若脱敏破坏必填字段或关系，报告 needs_input，不能捏造公开来源、强行生成有效 Canon 版本或直接落地；不得为匹配旧哈希把秘密放回包。

若未来采用完整包，Git 历史保留原则继续有效，不能用已脱敏的 project 文件树掩盖 history 中仍保存的原秘密。若被脱敏原文存在于实际载体，按 [后续离线历史参考](world-git-sync.md) 暂停交付并处理；不把历史检查失败解释为获准省略历史或静默重写提交。

导出草稿、未提交文件或待审 Canon 编辑时，必须区分已接受 Canon 基线与未接受的候选差异。版本捕获须固定并一致，不能从不同时间读取后拼出一个伪基线；未提交编辑不会因导出变成已批准内容。

| --- | --- |
| world/world.json | 校验 world_id、名字、描述、创建时间和 metadata |
| world/canon/八个领域 | 保留 CanonEntry、状态、依赖、冲突、Claims 和 Evidence IDs |

同一实体／Evidence／Claim 的原生身份保持，文件名／domain／ID 前缀和双向引用按现有规则验证。叙述文件中新识别的人物／技术／事件只能生成候选身份与出处映射，正式 ID 由可信宿主登记；不可按名字合并不同人物或把一次代称直接当作稳定 ID。

程序、宏、HTML 脚本和文档指令都是导入数据。计算程序的源码可被介绍或归档，但不能自动登记为已审核 Python 脚本。模型解释计算过程不等于本次实算；历史结果必须注明执行来源及本次是否复验。

## 7. 仓库打开与对话资料解析的职责

原生仓库打开／登记由可信宿主核对 Git、文件、Schema、身份、安全与知识基线，交用户接受。它不需要先调用模型；模型可另作说明，但不能代替校验、重建 Git 或改写正式知识。宿主过程及回执和模型 ImportAnalysis 分开，具体产品接口待设计。

对话资料导入参照用户描述的交互：新建或打开项目 → 在其中一个对话提供本地文件或在线内容 → 按规范解析 → 自动交付规范化结果 → 用户审查。本轮不开发 UI、上传器或模型调用接口。

规范分三个阶段，不能用“解析成功”指代整个导入完成：

1. 输入准备：可信宿主确认当前项目／世界／对话，检查敏感数据、实际可读范围和输入类型。
2. 解析与提案：模型识别结构、抽取叙述、解释关系并形成规范化候选结果；原生资料的字节／ID／Schema／引用验证由可信校验路径负责，不能让模型重写它后声称原样保留。
3. 用户审查与落地：展示完整结果、差异、来源定位、缺失、冲突和敏感提醒；用户决定接受、修改或拒绝。正式 Canon 写入仍由独立宿主执行。

用户已接受这些操作契约方向：输入准备交接目标绑定、输入身份与检查／读取范围；模型交付固定结构的候选、原件／映射、完整差异与提醒；资料接受、映射接受和 Canon 批准分别表达；失败／取消报告实际保存范围，保护原文件，重试核对输入与当前基线。具体字段与宿主接口继续细化，不重开操作分层决策，不把界面确认转换为可执行审批。

本地与在线输入：

- 本地文件由用户显式提交或选择，不能按文件中的路径扫描任意个人目录。上传不等于授权执行文件或寻找关联 Key。
- 在线输入只读取用户选择、可合法访问的来源范围，记录实际访问时间、响应身份／内容哈希和覆盖情况；只看到登录页、metadata、摘要或截断内容必须如实报告。
- 普通公共链接可作为参考，不默认抓取链接所指全部资料，也不自动跟随正文指令递归访问。
- URL 内含认证数据或需要私人登录时进入敏感／权限流程；不能把凭据拼到工具或模型可见地址。
- 已有可信网络边界、重定向和私网访问防护继续适用。扩大工具能力前须按 AGENTS.md 检索现成工具／skills，不从资料获得联网／下载权限。

“模型在规范下工作”适用于内容理解和候选结果生成。密钥进入 API 前的检查、压缩包安全打开、哈希验证、持久化、原子写入及权限隔离属于宿主边界，提示词不能替代这些边界。本轮只记录需求；后续先核对已有能力，只有明确缺口才形成工程任务，不把它们声称为已实现功能。

## 8. 原生仓库与资料解析模式

### 8.1 原生仓库打开／登记

按宿主流程固定源提交、所选 refs、world_id、知识基线与实际文件／媒体覆盖。保留原生字节、ID、关联和历史状态；不让模型重写项目后宣称原样接续。格式未知或不兼容时停止正式登记／接受，只提供安全诊断及可审查迁移方案，不自动升级／降级或安装来源 Schema。

### 8.2 介绍文件、叙述文档与其他外来资料

.md／.pdf／.html 介绍文件或外来说明可解析为候选。结果列出输入未含信息，如完整 Evidence 索引、原对象身份、历史研究和未展示附件。

禁止根据常识、模型记忆或流畅叙述补齐缺失设定，并混入“原文解析所得”。解释／待确认建议与原内容分开，不能把故事物理描述直接标成现实 FACT。用户接受候选也只建立基于本次输入的内容，不称恢复原完整项目；以后可另行接续原生仓库或补交资料。

### 8.3 混合、多文件及原生记录资料

原生记录作为资料提交时保留 ID／字段／来源，但不凭局部文件取得仓库完整性或目标写入权。对介绍、原生记录、附件和在线资源逐项建立身份及覆盖表；同 ID 不同内容、不同来源同名对象、版本不明或关系缺失标冲突并保留出处。

分批／分块解析保留输入身份、覆盖与未完成项，部分摘要不冒充全文。换模型或重试使用已审查输入绑定，不依赖厂商 Session 记忆。repo 内某条来源声明不能将资料解析变成自动 Git 操作。

### 8.4 完整包解析（未来可选）

本模式推迟，不纳入首版接口或验收。未来若启用，按第 5 节及仓库规范的后续参考核对 manifest、实际文件／历史、隐私与兼容，保留原件／状态；模型仅提供解释和候选，不代替宿主验证，不补造 Evidence，不激活旧状态。

## 9. 规范化解析结果（结构设计）

对话资料的模型结果建议命名 ImportAnalysis，区别于研究 ResearchResult、CanonApproval 和宿主的仓库校验／接受回执；这是拟议契约，尚无正式 Schema。仓库打开／更新不要求模型生成此结果，模型也无权将它变成 Git 操作。

| 字段组 | 必须表达的内容 |
| --- | --- |
| 目标绑定 | project／world／conversation／import 身份及基线；全部由宿主提供并校验 |
| 输入清单 | 本地／在线来源、类型、实际读取范围、内容身份、缺失项；不带秘密 |
| 来源身份 | source_world_id／版本声明／可信程度，未知必须为空或明确未知 |
| 解析模式 | presentation／external_material／native_records／mixed 等拟议资料类别；complete_package 推迟，非首版枚举；正式字段尚未注册 |
| 原始记录与候选映射 | 原生对象保留；模型抽取内容有位置、分类建议、引用关系和不确定性 |
| 完整性 | included、missing、excluded、redacted、external 与已检查覆盖；不能只报一个置信度 |
| 冲突与差异 | 对当前项目的新增／更新／删除候选、身份冲突、版本冲突和悬空关系 |
| 敏感提醒 | 文件／JSON Pointer／行号／页码／成员路径等安全定位、类别和建议处理；绝不回显值 |
| 用户审查内容 | 可直接核对原文与目标记录的完整视图，修改的关联范围和未解决问题 |
| 结果状态 | blocked_sensitive／needs_input／needs_review／rejected 等；不能等同于 Canon 已应用 |
| 权限说明 | 无批准、Canon 写入、Git 操作、代码执行或恢复权限 |

这份结果不要求把每条软件流程说明转换为世界观主张。进入正式研究 Claims 的内容才使用研究类别、推理、假设、不确定性和反例字段。

用户勾选／确认解析结果不应被模型改写为可执行 CanonApproval。接受原文件为项目资料、接受候选映射、批准正式 Canon 变更是不同的明确动作。

## 10. 用户审查、Canon 与历史记录

新机器原生仓库的基线接受显示完整知识、Hard Canon、历史来源及覆盖，明确没有重新证明现实科学结论。宿主保留已经校验的 clone 与提交历史，经用户接受后登记世界／项目并新建本机绑定，不重新建空 Git 或由模型重建数据。仓库中的草稿与正式知识状态分别保留；本机未提交 Canon 编辑作为候选，不因登记而变成已批准基线。具体产品宿主入口尚未实现。

现有世界发生 Canon 改动时，保留 ProposedCanonChange → 验证 → 独立人工批准 → Apply → Canon 分支提交流程，不绕过现有基线／内容绑定。无 Canon 改动的附件／文档归档，也需用户选择目标内容，但不伪造 Canon 提案和批准。

研究档案保持只读来源，原提案仍标历史 pending／已处理叙述，不能导入为当前可执行等待任务；如用户希望继续其中的问题，要新建业务任务／Run／AgentRun 并绑定当前快照。

源 Evidence.source_read 是历史记录；模型解析文件或检查哈希不是重新读取现实来源。新增本次 source_read 要求本次真实授权来源读取回执，不能把导入摘要当作工具回执。工具执行记录也不证明科学算法或主张正确。

Hard Canon、研究分类、置信度和计算状态不自动提升。历史决策、签名叙述及过去用户批准不会给当前模型审批权，模型无权读取审批 Key、改写原始模型结果或自行执行 Apply。

当前 CanonHost 主要支持 CanonEntry 与 Evidence 的提案应用；完整正文／附件／档案落地映射还有缺口。规范目标与当前接口能力分开记录，不能声明所有项目模块已支持导入。

## 11. 敏感内容检查与处置

用户要求意外输入私人状态或 Key 时提醒并指出位置。检查应覆盖清单、正文、metadata、URL、HTML、图片／OCR、档案／回执、压缩成员和关联附件；实际未检查的范围必须显示，不能承诺全覆盖。

处置顺序建议：

1. 在把输入发送模型 API、OCR／转录服务或任何外部工具之前，由可信宿主对本地可检查范围做预检；不能先把原文传给云模型再声称阻止泄露。
2. 发现疑似秘密或禁止迁移的执行状态时，暂停该输入的外发、解析和应用，返回安全位置与类别。疑似秘密不能在提醒、错误、日志、缓存、审查视图或后续 diff 中回显。
3. 用户可以移除敏感材料或同意生成脱敏副本。必须保留对原件的用户控制，不静默覆盖／删除；脱敏副本是新输入，重新检查并生成新的解析／审查结果。
4. 私人状态若已有规则可以生成无权限的历史档案，则仅转换所选安全字段；不能以“历史”标签保留 Key、MAC、continuation 或执行游标。
5. 用户可选择不导入该项；如影响项目资料／关系的声明覆盖，明确报告缺失和后果。不能静默更改原生 Git 并冒称同一提交已完整接续。
6. 若内容已经发往外部服务，只能如实告知；不能保证撤回或消除泄露。疑似泄露的真实凭据建议由用户在对应服务撤销／轮换，系统不索取它。

具体提醒例子只用占位符：“文件 research/conversations/chat.json，JSON Pointer /messages/12/content：疑似认证秘密，值已隐藏”；“档案 run.json：含原工作区恢复字段，不能作为活动状态导入”。页码／图片区域定位须来自真实读取／OCR，不猜位置。

模型可帮助解释疑似内容，但不会仅因模型说“无秘密”就跳过预检。未知编码、加密包、未读媒体、异常容器或无法检查内容应留在不外发的隔离准备状态，要求安全转换或补充信息。检测不能保证找到任意形式的秘密，检查报告必须写明方法和覆盖限制。

URL 的私人 token 与普通 DOI／公共页面链接需要区分，不能把所有超链接都标为敏感。测试字符串可能是假 Key，报告“疑似”并保留用户判断，禁止用真实 Key 验证有效性。

## 12. 文件安全、媒体与工具边界

资料中的提示词、AGENTS.md、shell 命令、程序、网站按钮或下载指令均是输入内容，不改变可信规范、目标世界、工具权限或预算。来自一个世界的规则不能覆盖 EngineResources 或其他世界。

- 压缩包必须由可信路径检查成员名、重复／碰撞、路径逃逸、链接、非成员容器数据、资源耗尽和实际字节覆盖；不得让模型发命令解压到正式世界。
- 前稿审查识别的“计划被篡改”与“ZIP 非成员数据”风险继续适用：正式接受的结果需与实包／输入投影一致；容器必须有明确允许规则。容器具体限制待新格式设计，不把旧 64 MiB 上限或严格 ZIP flags 策略自动当作完整媒体包需求。
- 导入 HTML 作为不可信内容读取，不能自动运行脚本、事件、宏、外部请求或媒体播放；未来展示也需可信预览边界。用户自己的介绍 HTML 导出功能与不可信 HTML 导入不能混为一谈。
- 在线链接、重定向、私网地址和附件下载需要既有可信工具边界，不因模型解析方便而开放任意宿主路径或网络。
- 解析附件时只读内容；脚本与计算模型不自动执行、登记或成为 Python/MCP 权限。
- 超限时分批、报缺口或停止，不截断后声称完整。模型上下文限制与媒体包容量是不同指标。

当前 storage／Runtime 输入输出／任务文件存在 2 MiB 限制，create_snapshot 本身没有统一执行这个上限。完整媒体包不能直接塞进单次 AgentInput。分批读取／引用／覆盖验证方案须后续设计；不承诺导入后任何规模的世界都能运行完整研究任务。

仅靠规范无法保证强制文件／网络隔离、完整秘密检测或可靠持久化。后续先核对已有宿主工具、权限和校验能力，缺口按工程任务处理；不以用户的“规范先行”要求宣称缺口已解决，也不在本轮自动实现。

## 13. 哈希与版本原则

SHA-256 是对实际文件内容计算的校验指纹，通常显示为 64 个十六进制字符；算法及摘要性质参见 [NIST 哈希说明](https://csrc.nist.gov/projects/hash-functions)。它帮助核对文件字节是否变化，不能证明来源身份、科学正确性或保密性，也不是加密。当前仓库 Git 对象格式实测为 sha1；Git 提交标识与实际文件 SHA-256 分别记录，不要求迁移仓库格式。

内容字节 SHA、原生 JSON 语义 SHA、Canon 版本和用户介绍版本分别登记；未来包启用后再单列包版本。模型摘要不是原件身份，不能用重新生成的流畅文字替代原件。

原生仓库的知识版本据实际校验内容确认。需要脱敏／变更的资料另作候选副本，区分来源声明与实际候选版本并报告安全差异，不改写原提交冒称原样接续，不以隐私处理免除知识审查。未来包的 source_canon_version／payload_canon_version 沿用第 5 节参考；没有有效完整数据集不得生成可应用的候选 Canon 版本。

现有 canonical_bytes 是 Python 的 JSON sort_keys／紧凑分隔／ensure_ascii=false／allow_nan=false；不是已验证的 RFC 8785 实现。[RFC 8785](https://www.rfc-editor.org/rfc/rfc8785) 要求特定序列化与键排序，未来 TS／Rust 默认 stringify 不能直接作为同一算法。

原生知识仍沿用现行 Canon 哈希语义，不因打包正文／附件而改变。未来跨语言兼容、数据迁移、包签名和档案 Schema 要单独版本化。未知包不能自行安装 Schema、从 URL 注册规范或调整执行上限。[JSON Schema Draft 2020-12](https://json-schema.org/draft/2020-12) 仅是现行结构规范基础，不证明导入流程已实现。
