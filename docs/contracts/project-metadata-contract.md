# 项目元数据与身份／版本机器契约（文档设计草案）

本文件维护行为与数据约束；实现范围、合入状态和工程验收统一见 [开发当前状态](../development/CURRENT.md)。规范、合成示例及未来验收条件不授予执行权限。

适用于标准外部世界 Git 项目。本文细化 [主契约](world-portability-contract.md)、[目录规范](world-project-structure.md) 与 [Git 接续规范](world-git-sync.md)，沿用系统／世界／宿主分离、一个项目一个世界观及多个对话、原生 Git 主载体和既有共享边界。不要求完整包或模型解析才能打开原生仓库。

## 2. 权威来源与存放位置

| 概念 | 唯一权威／归属 | 可校验的关联 |
| --- | --- | --- |
| 世界身份、名称、描述 | world/world.json | project.json 的 world_id 仅作一致性关联；产品名称展示读取 world/name，不再存第二份名称／描述 |
| 产品项目身份 | 根目录 project.json 的 project_id（已绑定并接受后） | 本机登记与对话／档案引用该 ID；来源文件仍是不可信输入，未接受前不改变目标 |
| 世界作品的展示版本 | 根目录 project.json 的 display_version | 文稿、介绍作品和发布说明只捕获生成时的值及来源，不另建可独立漂移的当前世界版本 |
| 项目组织格式 | 根目录 project.json 的 project_format_version | 表示该项目字段及目录职责契约；不替代各核心文件的 schema_version |
| 本机绑定与操作状态 | .axiom/local 及外部可信宿主 | 不写入共享 project.json；精确接受／批准／恢复入口另行设计 |
| Canon 内容身份与 Git 来源 | 现行快照验证结果及实际 Git 提交 | 由宿主核对，不在 project.json 存可自行更新的副本 |

project.json 可随世界 Git 提交，但不含 workspace_id、路径、宿主 ID、用户名、remote、Key、厂商会话、批准／MAC、恢复字段或自由 metadata。仓库地址与认证只由宿主显式选择；文件中的任何字段不授予联网、写入、执行或审批权限。

不向 world/world.json 的 metadata 增加另一份 project_id 或 display_version。若旧材料已有同名自定义值，仅作为来源声明报告差异，不把它默认为正式第二权威，也不擅自删除。

## 3. 拟议 project.json 的最小字段

拟议格式版本 1.0 的完整顶层集合恰为以下四项；全部必填，字段名区分大小写。没有隐藏默认值或本阶段扩展容器。

| 字段 | 类型／约束 | 作用与生成／修改主体 |
| --- | --- | --- |
| project_format_version | string；本草案只定义精确值 "1.0" | 可信宿主依据经审查的契约写入；用户改变设定不自动升级格式 |
| project_id | string；拟议 PRJ-UUID v4，规则见第 4 节 | 新项目由可信宿主生成；同一共享项目在 clone／fetch／换机中保留，模型不能分配或改写 |
| world_id | string；符合现行 WLD-UUID v4，且与同一基线的 world/world.json 精确相同 | 对世界权威身份的关联；绑定时由宿主读取并校验，不能单独改成另一个世界 |
| display_version | null 或受限 string，规则见下文 | null 表示作者未设置展示版本；字符串由用户明确设置或接受，不自动根据提交／日期生成 |

不新增 created_at／updated_at、世界名称／描述或快照／提交字段。项目身份与版本的历史通过实际 Git 和未来内容绑定回执追溯，不让一个自报时间证明新旧或真实性。

### 3.1 字节与类型约束

- UTF-8、无 BOM、严格 JSON，顶层必须是 object；重复键、非有限数字、无效编码和不合法 Unicode 代理码点拒绝。字符串不转换为数字、布尔或其他类型。
- 四个字段必须齐全；缺字段与显式 null 不等价。只有 display_version 可以为 null，其他字段不能为 null 或空字符串。
- 未知字段、字段别名和大小写变体不丢弃、不自动映射；返回兼容诊断，停止正式登记／接受。原件保留在安全准备范围。
- 字段顺序和无语义空白不改变字段含义；原文件字节仍有独立身份，不能因解析等价就改写后称原样保留。
- 本文不注册新的大小上限。现有读取上限仍如实报告，超限不能截断后声称完整；未来宿主需确定项目元数据的明确资源限额。

### 3.2 display_version 的精确约束

字符串长度为 1–64 个 Unicode 标量值，首尾不能是 U+0020 空格；不含 U+0000–U+001F 或 U+007F–U+009F 控制字符，不含代理码点。Python／TypeScript／Rust 的实现必须采用同一标量计数和范围，不能把 UTF-16 code unit 长度当作该长度。

不做隐式 trim、Unicode 归一化、大小写转换、补前缀或 SemVer 解释。"第二版"、"v1.2" 均可作为标签；"" 无效，null 才表示未设置。比较标签只比较确切字符串，不能据此排序提交、计算 Canon 版本、证明已发布或决定同步。

作为共享用户文本，标签仍需未来宿主的敏感预检和安全展示；满足类型规则不意味着没有秘密。发现疑似秘密只提供位置／类别，不在诊断回显原值。

## 4. 身份格式及稳定性

WLD、现行研究标识与 workspace_id 沿用现行实现。PRJ 已在本步 ids.py 和 Schema 中登记，new_id("project") 可显式生成身份，但不会创建／登记项目或修复输入。CNV 仍仅是拟议前缀，new_id("conversation") 不支持。

拟议 project_id／conversation_id 分别使用以下精确模式；仅允许 ASCII 小写十六进制和标准连字符，不接受前缀别名、大小写归一化或缩写：

```text
project_id:
^PRJ-[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$

conversation_id:
^CNV-[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$
```

| 身份 | 稳定范围 | 生成与接续 |
| --- | --- | --- |
| world_id | 同一世界及其实际取得的原生历史 | 现有可信 world create 生成；标准接续保留；名称或相同局部实体 ID 不证明同世界 |
| project_id | 同一共享产品项目及其对话／档案 | 未来宿主为新项目生成；用户已确认同一仓库跨机保留。登记到本机是建立关联，不另生成替代的本机 project_id |
| workspace_id | 一个本机路径绑定的世界工作区 | 现行无前缀 UUID v4；新机器／独立 clone 建立新绑定，不能复制旧 workspace.json 或重签旧状态 |
| conversation_id | 一个业务对话及其安全归档引用 | 未来宿主创建新对话时生成；共享同一历史对话保留来源 CNV，不转换成厂商 Session，不自动恢复活动对话 |
| TSK／RUN／ARN／ART 等 | 现行研究任务和执行记录 | 沿用现行标识／绑定；档案保留来源标签，继续研究要新任务、新执行与当前固定快照 |

project_id 一经分配不能因改名、版本标签、移动、clone、分支或机器变化而重生成。普通分支／PR 和保留身份的仓库 fork 仍是同一项目／世界的历史路径，不自动派生新世界。用户若希望派生独立世界／项目，另审身份与引用映射，不在本阶段定义复制命令。

标识形式合法不证明唯一、归属、真实性或授权。宿主还须核对被选择的项目、世界、来源与本机登记；发现同 ID 冲突，不能让模型生成一个新 ID 来掩盖。

## 5. 世界、项目、对话及对象引用

1. 已绑定 project.json 的 world_id 非空，并精确等于同一捕获基线的 world/world.json；一个项目不能同时绑定多个世界。
2. 新对话由操作者选择目标项目后创建，目标 project_id 由宿主提供，不从用户上传文件、标题、模型输出或历史 Session 推断。
3. 对话归属键为 (project_id, conversation_id)，已绑定世界另校验 world_id。核心世界对象仍按 world_id、对象类型和现行业务 ID 校验；project_id 表达容器／目标，不取代核心 world_id。
4. 同一项目可有多个对话；同名对话不合并。对话与研究任务可多对多关联，不改为一对一，不把 CNV 当作 task_id。
5. 已绑定对话／档案与来源项目不一致时停止常规接受，不自动改名、重新分配 CNV 或跨项目搬运。跨项目／跨世界参考另交付明确映射。
6. 同 CNV 的档案在多台机器出现时，先比较实际来源、内容身份及关联；不能仅凭 ID 相同覆盖。不同内容需要差异审查；档案格式／修订字段另行定义。
7. 项目内已接受知识可以供多个对话使用，未审材料与候选仍由各自导入／任务绑定隔离。项目 ID 相同不授予读取他人未审内容的权利。
8. 固定研究快照不受项目版本标签、其他对话接受结果或仓库更新影响。引用档案不能绕过同任务首轮独立。

例如来源 TECH-001 和目标 TECH-001 若 world_id 不同，就不能按文件名或名称覆盖；同 world_id、同对象 ID、不同内容也必须比较基线与状态，不能视为天然相同。

## 6. 未绑定准备状态与正式项目文件

未绑定的新产品项目可以由未来宿主保有 project_id，并以 world_id = null 记录其准备状态；该对象属于私人宿主／产品准备记录，**不是本契约的共享 project.json**，也不表示现行 CLI 支持此功能。它可以组织用户选定的对话材料，但没有正式世界、Canon 或恢复权限。

共享 project.json 只表达已绑定的项目元数据。不能为了满足四字段格式而捏造 world_id、建立正式空世界、把 null 写进已绑定文件或根据对话标题猜身份。

| 情况 | 拟议处理 |
| --- | --- |
| 打开已经 clone 的原生项目，未预先选择产品项目 | 在安全准备范围检查来源元数据／世界；用户接受后登记来源 project_id，建立本机关联，不必先创建另一个临时项目身份 |
| 新准备项目后来明确建立自己的世界 | 经独立宿主步骤验证／接受世界身份后，保留已分配的 project_id，生成拟议已绑定元数据；世界创建与保存实现另行授权 |
| 准备项目选择接续同 project_id 的原生仓库 | 比较源 world_id、输入和已选目标，交付接受候选；null 到已绑定不是靠模型填字段完成 |
| 准备项目已有 project_id，来源为另一 project_id | 停止默认接续，展示两个项目身份；可以另行打开来源为独立项目。若迁移原准备对话／材料，必须另审映射，不自动把准备项目改成来源 ID |
| 已绑定项目接收无 world_id 的普通资料 | 在当前目标中生成来源身份未知的候选；不能把它当作合格原生项目文件 |

准备阶段的历史记录如原本 world_id 为 null，绑定后也不自动改写原记录或声称早期对话已基于正式 Canon。未来档案可另外记录绑定关联及后续新消息，完整格式不在本阶段。

## 7. 本机登记与跨机重复处理

本机登记是未来宿主的私人索引，至少在概念上关联共享 project_id／world_id、所选路径及当前 workspace_id。[仓库宿主回执草案](repository-host-receipts.md) 已细化本次操作的绑定与结果条件；登记索引格式、可靠保存与并发实现仍未实施。这些值不放入共享 project.json。

| 输入／本机状态 | 处理要求 |
| --- | --- |
| A／B clone 同一有效项目 | 保留来源 PRJ／WLD；各自建立新的本机工作区，排除旧凭据／批准／checkpoint；安全档案只作资料 |
| 同路径、同 project_id／world_id、有效旧绑定，再次打开 | 复核路径、当前精确提交及本机绑定；满足同一已接受内容条件时复用登记，不重复生成身份；有更新仍须比较和接受 |
| 同 project_id／world_id，在本机出现另一独立 clone 路径 | 可以表示同项目的另一个工作区，但必须显式选择／登记该路径并建立新的 workspace_id；不悄悄改变原登记或当前研究目标 |
| 同 project_id，不同 world_id | 身份冲突，停止常规登记／接受；保留双方，交付诊断，不自动改 world.json 或项目 ID |
| 不同 project_id，同 world_id | 项目身份关系待审；不能只凭 WLD 合并本机项目、对话或文件，也不能宣称世界内容损坏。派生／迁移关系另行审查 |
| 相同 PRJ／WLD，不同 Git 提交或工作树内容 | 不等于同版本；按精确来源、知识基线及候选差异处理，不自动覆盖或接受 |
| 目录移动、旧 workspace.json 路径绑定不匹配 | 保留并报告现行拒绝；需要独立迁移／重新登记方案，不手改旧绑定或自动重签 |
| 目标路径已登记到其他身份 | 停止常规打开，不替换索引、不清理文件；展示绑定差异并交用户处理 |

多个工作区共享 project_id 不代表共享任务、审批 Key 或恢复权限。每次后续研究、导入及同步操作均由宿主绑定显式目标与固定基线；任何一个本机路径的变化不能自动传播为其他工作区已经接受。

## 8. 版本的独立含义

| 值 | 含义／权威 | 变化条件与限制 |
| --- | --- | --- |
| display_version | 用户作品标签；project.json 唯一存放当前标签 | 用户明确设置／接受；可为 null，不排序、不自动证明发布或知识变化 |
| project_format_version | 拟议项目组织／字段契约版本 | 契约变化经审查后确定；本草案只定义 1.0，不按字符串大小推断兼容 |
| world／各文件 schema_version | 已安装核心结构格式 | 现行世界 Schema 为 1.0；不因 display_version 改动而变，不从世界提供的 Schema URL加载规范 |
| canon_version | 实际核心知识内容的固定版本 | 沿用现行快照验证／哈希算法；不能由标签、旧自报值或模型摘要生成 |
| Git 对象格式及精确提交 OID | 实际取得的提交和父关系 | 来自真实 Git；同文件树但不同提交仍是不同提交；未提交字节不冒称已在提交中 |
| workspace layout_version | 本机执行状态布局及绑定 | 现行 workspace.json 为 1.0；与项目结构版本不是同一字段，不自动升级旧绑定 |
| engine system_version／资源指纹 | 正在使用的可信软件及规则 | 由 EngineResources／宿主取得；世界内不覆盖系统版本或恢复指纹 |

Git 提交 OID 的表示须同时知道实际对象格式，不能把系统仓库当前 sha1 推广为所有未来世界。本文不定义新的 Git 支持表或迁移能力。

### 8.1 展示版本的捕获与修改

- 仅修改 project.json 的 display_version，不改变 world 核心文件时，现行 Canon 内容版本应保持一致；project.json 字节和提交身份另行变化。
- 世界核心文件的有效内容变化会按现行规则影响 Canon 版本，即使 display_version 未变。Git 还有作者文件等范围，Canon 快照不是整个项目快照。
- 未来介绍作品捕获生成时的展示标签、来源提交／知识基线及日期；历史作品不被新标签自动重写，也不冒充当前作品。具体导出规范继续保持空占位。
- 提议改标签仍要展示来源和目标差异并由用户接受。只改项目标签不伪造 CanonApproval；同时含 Canon 修改时仍走既有独立审批。
- 不新增“世界版本号”副本，不以 world.metadata 中任意值、文稿题名或 Git tag 替代权威标签；这些可以作为独立来源声明比较。

### 8.2 哈希边界及跨语言约束

现行 canonical_bytes 使用 Python JSON sort_keys、紧凑分隔、ensure_ascii=false、allow_nan=false；不是已验证的 RFC 8785 实现。本文不新增 project canonical hash、项目总版本或跨语言序列化 profile。

未来宿主可对实际 project.json 字节取 SHA-256 作输入指纹；这与解析后的字段比较、现行 Canon 语义版本和 Git OID分别表达不同身份。格式检查或字节哈希不证明来源可信、内容真实或无秘密。

Python／TypeScript／Rust 可以实现本文四字段与身份约束，但核心 Canon 哈希仍必须调用现行可信实现或在独立兼容阶段证明等价。不能用默认 JSON.stringify、键顺序或 Unicode 归一化生成所谓相同 Canon 版本。

## 9. 基线捕获与接受绑定的最低要求

未来仓库宿主需在本次安全准备中固定至少以下事实：操作者选定的目标、本机绑定（如有）、实际源提交及对象格式、该来源的 project.json／world.json 身份、原生知识基线、实际工作树差异和覆盖。拟议字段关系见 [仓库宿主回执草案](repository-host-receipts.md)，尚无可执行接口。

不能把提交 A 的 project.json、提交 B 的 world.json 和后来改动的知识文件组合成一个伪基线。检查期间变化、文件缺失或读取范围不足时停止正式接受，交付重新捕获的比较结果。

已提交元数据与本机未提交编辑分别表达。project_id／world_id 的未提交差异属于冲突候选，不能成为自动重定项目／世界的依据；未提交 display_version 也要显示来源状态，不说成远端已合并标签。

通过本文数据检查只是满足一个必要条件；仍须完整仓库安全／关系检查、用户接受和可信宿主保存。准备／检查成功不生成 Canon 批准、PR 合并批准、执行登记或恢复权限。

接受前重新核对内容及当前目标基线；任一绑定变化停止沿用原结果，不因 PRJ／WLD 相同继续覆盖。与 [Git 规范](world-git-sync.md) 的本地未提交／未追踪／分叉保护及固定研究快照要求一致。

## 10. 兼容及安全诊断

本节列出完整契约的诊断语义；本步只读 CLI 已实现其中格式／缺失／关联／有限变化的子集，具体 scope 与实际返回状态见使用说明，其他诊断仍为未来条件。它们不是 ResearchResult 的事实类别。未来完整宿主对多个问题应记录实际覆盖和发现事项；涉及疑似秘密时先阻止外发和接受，仅安全定位，不回显值。本步没有敏感检测，结构合法不意味着安全或可接受。

| 场景 | diagnosis_code／含义 | 允许的后续 |
| --- | --- | --- |
| 四字段及世界关联有效 | metadata_valid：元数据检查条件满足 | 继续宿主其余检查与用户审查，不直接登记或写世界 |
| 整个 project.json 缺失，核心世界有效 | legacy_metadata_missing：已有核心世界，不是本文产品格式 | 安全只读检查；生成经用户审查的最小元数据候选。不自动写入、生成 ID或改旧历史 |
| 必填字段缺失或类型／格式错误 | metadata_invalid | 保留原件、安全定位；补充或修复须形成新候选，不能使用隐藏默认值 |
| project_format_version 未知 | project_format_unsupported | 安全只读诊断，等待经审查的迁移方案／兼容实现；不自动安装来源规范 |
| 未知字段／别名 | project_fields_unsupported | 不丢弃原字段，等待字段处置方案；不能悄悄剥除后自报原样兼容 |
| project／world 关联不一致 | identity_conflict | 停止接受／登记，比较来源与目标，不自动选一边为真 |
| 对话归属不一致 | conversation_binding_conflict | 停止该材料常规接受；全对话格式及迁移另定 |
| 本机路径／工作区绑定失配 | workspace_binding_conflict | 保留旧状态，交付迁移或重新登记方案，不重签 |
| 捕获内容或目标基线已变化 | baseline_changed | 重新捕获／检查／审查，不复用旧接受结果 |
| 未取得必要文件、对象或未知检查范围 | inspection_incomplete | 列出实际缺口；不能称有效完整基线或接受完成 |
| 疑似秘密或禁止共享状态 | blocked_sensitive | 阻止外发及接受，只给位置／类别；脱敏副本作为新输入重审 |

现行核心 CLI 可能校验一个缺少 project.json 的世界成功，这只说明现有核心条件满足。未来产品登记必须另报告本文元数据条件，不回写“旧世界无效”或暗示基础分离未完成。

迁移候选至少列出原输入身份、当前目标、字段／ID／关系差异、版本变化、内容影响和未解决项。密钥或敏感 before 值不得进入候选／diff；生成候选不授予写入、批准或迁移权限。遗留项目是否采用新 PRJ、如何关联已有材料，需按实际输入审查，本阶段不生成通用迁移器。
