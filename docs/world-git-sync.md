# 世界 Git 仓库接续、多电脑与多人协作规范

日期：2026-10-08；2026-10-09 补充共享项目身份，2026-10-10 补充宿主回执草案。状态：用户已确认标准世界 Git 仓库为主载体，换机直接 clone；完整数据包推迟为可选离线备份／迁移。本文是操作规范，仓库打开／登记／校验、GitHub 接入及同步接受的产品接口尚未实现。

同一世界在新电脑 A 上取得同一 GitHub 仓库，修改经工作分支、PR、自检、用户复查与明确批准后合并；主要电脑 B 可请求该仓库已合并的明确版本并审查更新。多人使用仓库访问权限协作，仍遵守项目审查及 Canon 规则。此流程不要求先导出或下载完整数据包。

本文依 [主契约](world-portability-contract.md) 和 [项目目录规范](world-project-structure.md) 延伸，不授权本轮 clone／fetch、配置 GitHub、操作正式世界或实现新功能。

## 1. 三种数据各有职责

| 数据 | 共享内容 | 本机处理 |
| --- | --- | --- |
| 标准项目文件树 | 已提交到所选仓库的世界知识、作者文件、安全历史档案、附件与索引 | 保留原相对路径；实际未提交／未上传材料和外部资源另行标注 |
| 原生 Git 历史 | 实际取得的源提交、文件树、父关系及所选远端分支／标签 | 通过标准 Git 接续，保留提交标识；不复制源电脑的整个 .git |
| 宿主与 .axiom/local | 凭据、Key、工作区绑定、活动调用、签名批准／恢复状态 | 不随 GitHub 迁移；新电脑新建绑定，旧电脑保留自己的状态 |

world_id 表示同一世界，在 A／B 上保持一致。用户已确认 project_id 随同一仓库跨机保留，各机 workspace_id、路径绑定、凭据和审批 Key 分别管理；共享提交历史不能令 A 的执行批准／checkpoint 在 B 上生效。本机登记是建立与共享项目的关联，不重新分配 project_id；来源文件不能替代宿主选择的目标项目。缺失元数据、身份冲突、重复工作区和版本关系见 [字段级契约](project-metadata-contract.md)。元数据格式／世界身份已有最小只读检查，完整仓库检查／登记接口尚未实现，不能将这两个文件检查当作 Git 接续验收。

GitHub clone 提供仓库文件和 Git 历史，是换机接续的正常路径；clone／fetch 的实际分支、对象与深度配置决定取得范围。浅克隆、部分克隆、尚未取得的 refs 或不在远端的本地提交不能自报为完整远端备份。依据 [GitHub 克隆说明](https://docs.github.com/en/repositories/creating-and-managing-repositories/cloning-a-repository) 与 [Git clone 文档](https://git-scm.com/docs/git-clone)。

## 2. 标准仓库打开／登记／校验

用户可选择已经 clone 的本地目录，或明确选择远端与新目标位置后由未来宿主接续。产品“打开项目”应先完成以下受信任操作，不要求模型重建仓库或把原项目重新解析成另一套目录：

1. 固定操作者选择的本地位置／目标项目、预期世界和 remote；确认正式世界是系统仓库之外的独立普通 Git。已有不支持的工作区形态或旧绑定不自动迁移。
2. 在受限准备范围核对实际源提交、所选 refs／对象、项目文件和读取覆盖；检查路径、链接、配置及敏感内容。远端取回在隔离准备阶段进行，不能先在正式世界 checkout、执行来源程序或向模型外发再检查。
3. 校验 world/world.json 的 world_id、核心 Schema、ID／关系和 Canon 内容基线；扩展档案按已定义契约校验，未知格式只报告／保留安全原件，不能伪称已有完整支持。
4. 展示仓库／世界身份、精确提交、完整世界内容与 Hard Canon、历史覆盖、文件／附件可用性及未解决事项；用户明确接受后才登记产品项目与本机工作区。
5. 保留已校验的原生 Git，不重新建立空历史，不让模型改写知识以匹配版本。新机器建立新 workspace 绑定、外部宿主配置与专用审批 Key；来源的旧 .axiom/local／凭据／批准不启用。
6. 已登记项目再次打开时核对原绑定和当前基线；发现世界或路径改变时停止常规打开，交付迁移／重新登记方案，不自行重签。

来源仓库地址、AGENTS.md、项目脚本、hooks／filters／外部驱动和配置只是输入数据，不能提供执行或联网权限。可信宿主需控制 clone／fetch／checkout 使用的配置及过程，不加载来源的执行规则，也不复用含认证参数的 URL。历史结构／连通性检查不替代隐私检查：实际接收的对象、metadata 与文件须有可核查范围；不能只扫最新文件树或声明 refs。具体隔离取得和检查接口尚待实现，不将普通 clone 命令本身宣称为安全沙箱。

如果输入历史含秘密，暂停外发、登记接受和应用，安全定位并交用户处理；不能为接续而保留秘密、静默过滤历史或自动重写提交。既有本地仓库原件保留；新取得的未审内容停留在本次受限准备范围，不进入正式世界或模型上下文。

此处“接受已有世界基线”不是对现实科学结论的重新证明，也不是执行旧批准。现有 CLI 尚无本文完整产品登记入口；不能把规范中的步骤当作已经可运行的命令。

## 3. Git 所能同步的内容与覆盖

只有实际提交、推送并取得的内容才是共享版本。用户自建的安全文件仍属于项目，不因不在示例目录中就被遗漏；若尚未提交或传输，应明确列出未共享项，不能用 clone 成功概括整个私人目录已迁移。

可共享研究档案须先由可信宿主按安全字段生成独立只读视图、保留原业务内容／关联并说明排除项，放入 research 等项目目录，再经内容审查纳入 Git。这个档案整理／持久化接口尚未实现；不能直接复制 .axiom/local，也不能声称现有活动日志会自动随 Git 上传。研究原件、本机 checkpoint 和原始模型输出不为共享而覆盖。

媒体／大型论文仍按项目及外部资料库策略处理。Git LFS 的仓库指针和实际大文件分开，取得提交不证明已取得所有大文件：[GitHub LFS 说明](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-git-large-file-storage)。核对本次实际下载的 LFS／附件及外部资源，标明缺失、权限受限和仅引用项；不自动将外部资料库加入 Git。

GitHub Download ZIP／Source code 归档只提供某版本文件，不包含完整 Git 历史：[来源归档说明](https://docs.github.com/en/repositories/working-with-files/using-files/downloading-source-code-archives)。可作为资料输入，但不能当作标准 clone 接续；系统应如实说明缺失，不因此要求所有用户改用完整包。

## 4. 新电脑 A 与多人协作

A 的正常接续路径：

1. 用户明确选择世界仓库与目标位置，取得标准 Git 克隆；宿主按第 2 节在安全准备范围验证，再让用户接受并打开／登记。
2. A 保留同一 world_id 与原生历史，建立自己的本机绑定，不恢复 B 或其他协作者的任务／厂商会话。
3. 在工作分支修改；正式 Canon 仍走 ProposedCanonChange → 验证 → 独立人工批准 → Apply。文稿、附件及档案也明确纳入本次文件清单。
4. 上传前检查待上传文件、提交历史和目标 remote 的自动执行入口；之后推送工作分支、提交 PR、自检并交用户复查。
5. 用户明确通过精确源提交／目标基线／合并投影后才能合并，合并前再次核对；任一绑定变化须重新检查与复查。

多人可通过 GitHub Collaborators 等仓库访问机制取得协作权限，依据 [GitHub 协作者说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/inviting-collaborators-to-a-personal-repository)。访问权限不是项目审查的替代，也不授予模型批准或自动合并权。实际账号权限／目标仓库能力由宿主核对，不声称 GitHub 默认已强制本文所有规则。

协作者采用各自本地工作区、工作分支和 PR；发生并行修改时比较源提交、目标基线和完整内容，保留各方历史／资料并交付冲突方案。不同人的本机审批 Key 与恢复状态不共享。研究任务仍使用固定快照，不能通过共享聊天／档案绕过同任务首轮独立。

首次发布、自动执行入口、上传前隐私检查和合并批准的具体要求沿用主契约第 4.3 节。仓库访问或 PR 历史不自动证明当前用户已批准本次 Canon 变更；本轮没有配置 Collaborators 或仓库保护规则。

## 5. 主要电脑 B 请求更新

用户在 B 请求“更新这个世界到该仓库已合并版本”时，宿主使用明确选择的世界、remote 和协作分支，先取回候选并固定源 SHA，展示与 B 当前基线的完整差异。核对 world_id、对象关系、安全边界、历史连续性与资料实际覆盖；不按名字或时间较新就覆盖。

| B 的状态 | 处理 |
| --- | --- |
| 精确源提交及所请求资料的实际内容／覆盖一致 | 报告当前已经是所请求版本，不重复改写；文件树相同但提交 SHA 不同仍按祖先／分叉关系处理 |
| 本地干净且历史可以快进 | 校验版本与完整差异，按下述人工接受规则更新到精确提交；不另建无关基线而丢失历史 |
| 有未提交、未追踪的项目内容或路径冲突 | 保留原文件与差异，暂停会覆盖内容的更新，交用户选择保存、提交或合并；不自动 reset／clean／删除 |
| 本地有独立提交、历史分叉或不连续 | 保留双方提交，交付冲突／合并方案；不默认 rebase、强制更新或丢弃本地提交 |
| 身份不匹配、包含秘密、对象缺失或兼容未知 | 停止接受及应用，给出安全诊断，不自报更新完成 |

fetch 与更新当前工作树分别处理。技术依据见 [Git fetch](https://git-scm.com/docs/git-fetch) 与 [Git merge](https://git-scm.com/docs/git-merge)；具体宿主入口尚未实现，不执行来源指令或盲目 pull。

远端已合并版本的接受是独立人工宿主步骤：用户审阅明确绑定当前 B 基线和候选源提交的完整世界差异后，才允许更新。涉及 Hard Canon 时也不得把同步当作免审改写通道；现有安全边界保留，具体同步接受入口须另行设计。远端 PR 通过的历史不能伪造 B 的 CanonApproval，也不能执行旧 Apply；建立已接受的当前基线后，后续新修改仍走既有 Canon 流程。

更新保留 B 的 .axiom/local 和宿主设置，不能改写旧 checkpoint／签名或恢复旧调用。运行中研究仍使用原固定快照；旧批准与 Apply 若不匹配新基线应停止，不能重签或自行套用。更新窗口需协调世界写入并复核基线；取消／失败不得损坏 B 的现有世界与本机状态。

更新结果应列精确提交、知识版本、实际取回资料范围与未完成项，不能仅给模型摘要。取回候选和完成校验不是工作区已经更新。

## 6. 操作交接与首版契约验收

原有资料解析的四类交接继续有效，另以宿主回执描述仓库操作。2026-10-10 的 [宿主回执草案](repository-host-receipts.md) 已细化四类回执、完整比较／覆盖、接受内容绑定、登记／更新完成及失败／取消判定；仍没有 Schema、可信接受验证器或执行／保存接口：

- 输入准备：目标绑定、输入身份、来源位置、读取／历史／媒体覆盖与敏感检查；检查失败不外发原输入。
- 仓库校验交付：精确源提交／refs、世界与项目身份、原生知识基线、完整差异／覆盖和安全诊断；不要求模型重建 Git 或输出代替校验。
- 模型解析交付：只对选定资料理解／抽取，保留原件和候选映射、缺失／冲突及提醒；不授予 Git／Canon 权限。
- 接受与保存：资料接受、映射接受、Canon 批准、仓库登记及远端版本同步接受分别绑定内容／基线，由可信宿主操作。
- 失败／取消：明确实际保存范围，保留安全诊断和用户原件；重试核对输入与当前基线，不依赖厂商会话或旧权限。

回执草案还记录实际源码缺口：现行 CanonHost 的批准 JSON／MAC 可能位于 Git 提交说明，历史检查不能只扫描文件树。普通 JSON、自报 issuer或哈希不提供执行权；未提交／未跟踪／被忽略路径冲突均须保护。结果未知时不得报更新完成、自动重放或回滚，不套用研究恢复入口。

未来首版验收应证明：A 直接接续标准仓库；B 接续明确合并版本；多人分支／PR 仍经人工复查；身份／remote 不串用；未提交／分叉内容不丢失；历史秘密拦截覆盖如实；本机批准／恢复不跨机；缺失附件／本机未归档记录不自报完整；仓库打开无需包或模型重写。这里描述验收目标，不表示本轮授权实现。

本轮仅文档，没有进行上述功能验收。后续工程先核对 Git／GitHub 与现成工具能力，按 AGENTS.md 检索可复用工具，再对实际缺口立项。

## 7. 完整数据包：未来可选离线备份／迁移

完整包不再是换机／GitHub／多人协作主路径，移出首版契约验收与工程依赖。未来用户有离线传递、保留未提交安全材料或独立备份需求时，才另行确定范围并设计；不能因本文保留参考而自动生成／发布包。

### 7.1 保留的历史封装参考

以下为此前已审查的设计参考，具体封装、manifest、bundle 版本和恢复入口均推迟；若以后采用“完整包”，仍须保留其声明的 Git 历史、排除秘密及私人执行状态。优先复用现有 Git 能力，不开发新的 Git 历史格式。

项目树仍沿用原项目结构，历史载体放在封装层：

```text
<完整数据包>/
  manifest.json
  project/                    边界内完整项目文件，原相对路径
  history/
    repository.bundle         候选载体：自包含 Git bundle
```

优先采用现有 Git bundle 能力承载对象与 refs，具体 bundle／容器版本和导入映射待细化，不开发新的 Git 历史格式。官方说明支持从自包含 bundle clone／fetch；bundle 不包含工作树、索引、仓库配置和 hooks 等本机状态：[Git bundle 文档](https://git-scm.com/docs/git-bundle)。本轮没有调用这些命令或做 bundle 功能验收。

规范要求：

- 固定导出时的源提交、工作分支／HEAD、业务 refs 和内容基线，完整记录项目文件、历史载体与 refs 的实际覆盖。业务分支／标签可达的历史不得静默裁剪；其他 refs 与未纳入内容也需分类说明，不用未知引用自动获得执行权限。
- 新电脑用的完整包必须自包含，无未声明的旧仓库对象依赖；浅历史、缺失对象、分段历史或过滤对象不能冒充完整。未取得的远端分支／提交只能标未取得，不能声称完整备份远端全部历史。
- 在不改动内容的前提下保留源提交 ID、父关系、业务分支与标签。refs、Git 对象格式、原始 HEAD 和默认协作分支均写入可核查清单；来源 refs 不能未经目标映射就覆盖已有世界分支。
- 项目工作树与历史中的源提交分别校验。未提交文件、脱敏副本或从 .axiom/local 提取的安全档案可能不在源提交中，逐项登记为 payload 差异；不能宣称它们已经提交、合并或获得 Canon 批准。
- 未提交 Canon 差异继续作为候选，不因首次导入成为正式知识。首次接续的正式基线来自已核对的源提交；草稿／资料与正式基线分别落地，具体映射与批准入口尚待定义。
- 检查历史可达的所有对象内容与 metadata 是否越过隐私／世界边界，不能只检查最新文件树。发现秘密时停止完整包导出／外发，交用户处理；不保留秘密以匹配旧提交，也不私自重写历史、生成新提交 ID 后声称原样接续同一远端。
- 检查范围还必须覆盖载体实际携带／接收的全部对象、headers、metadata 与容器字节，不能只遍历声明 refs。可信宿主在隔离暂存中核对实际对象集合与所登记 refs 的完整对象闭包；未登记额外对象、对象过滤／缺失及未允许的非对象／尾随数据应拒绝，不能先存进正式世界再只检查可达对象。bundle verify 或对象连通性检查不等于秘密检查与实际字节覆盖验收。
- 整个 .git 中的配置、credential、hooks、对象外部共享绑定、个人路径和本机恢复记录不复制。历史载体的结构校验不替代秘密检查、世界身份校验或文件安全边界；不自动 checkout 未检查的来源文件、执行项目程序或启用来源 Git 设置。

历史内容需脱敏时，必须另行审查历史处理及旧／新提交映射与远端协调，不能自动 force push 或修改远端历史。此异常处理不表示历史保留需求重新待定。

### 7.2 未来包与远端版本的对应

以下仅适用于未来明确启用的离线包或正式包发布，不是当前流程：

世界仓库已合并的目标分支是共同提交版本的来源。完整包绑定明确的源提交／refs，代表导出时点，不会随 main 前进自动变成新版。

GitHub 的 Download ZIP 和自动 Source code 归档不含整个仓库历史，不能标成本文完整包：[GitHub 来源归档说明](https://docs.github.com/en/repositories/working-with-files/using-files/downloading-source-code-archives)。后续可以把系统生成的完整包作为同仓库关联的发布附件提供；发布位置／工具接入仍待设计，当前没有发布功能。

发布包需绑定该仓库的精确源提交和实际文件／历史覆盖，检查访问位置与内容身份；名称“latest”或 manifest 自述不能证明它是最新已合并版本。上传包也适用秘密、历史和自动执行入口检查。生成包不重新追踪进它所包含的项目／提交中，避免递归把历史包打包进新历史包；已有项目内旧包仍按主契约登记，不暗中遗漏。

同仓库正式发布包应绑定已合并的明确源提交。发布是外部写入，需在完整清单、实际 payload 差异、历史范围和秘密检查结果可审阅之后获得明确授权；源提交的 PR 复查不自动覆盖额外未提交草稿、档案或媒体。附加候选必须如实标注且不成为正式 Canon；自动生成／发布流程也须单独明确授权和检查执行入口，不把“支持下载包”理解为已获准后台发布。

未提交、未推送或没有实际传输的附件／档案不能被描述为 GitHub 已同步。若依靠外部资料库或发布附件，需记录实际可获取性与版本对应；另一台机器取回 Git 提交不等于已经取得全部媒体。

这些参考中的“完整包必须自包含”和离线恢复属于未来包验收，不纳入本次首版仓库接续。旧包若落后于所请求远端版本，只能说明实际源提交，不冒称最新或覆盖 B；不得凭包内声明取得 remote 或发布权限。
